01 — The Problem

A Monolith That Became a Liability

Meridian Financial's retail banking platform had grown into a large monolithic application over many years. What started as a pragmatic architecture had become a serious constraint on the engineering organization.

  • Coordinated release trains: Any change — even a minor UI update — required a full regression cycle and a synchronized release across all teams, slowing delivery to a crawl
  • Cascading failures: A bug in one domain (e.g., notifications) could destabilize unrelated domains (e.g., ACH transfers), with no fault isolation between modules
  • Scaling bottlenecks: Scaling any high-traffic feature required scaling the entire monolith — wasteful and expensive
  • Onboarding friction: New engineers took weeks to ramp up due to the deep coupling and shared codebase
  • Security complexity: Compliance and security changes had to be manually propagated across hundreds of interconnected components

Key constraint: This was a live platform serving millions of active banking customers. Zero downtime tolerance. Any architecture approach had to keep the lights on throughout the entire migration.

03 — Architectural Approach

How I Designed the Migration

1

Domain Analysis & Service Boundaries

Before writing a single line of code, I spent three weeks doing domain analysis using Domain-Driven Design (DDD) techniques — mapping bounded contexts by interviewing domain experts and analyzing data flows across the monolith.

  • Account Management — balances, account details, overview
  • Transaction History — records, statements, exports
  • Payments — ACH, C2C, wire transfers
  • Notifications & Alerts — multi-channel delivery
  • Customer Support — ticketing and case management
  • Mobile Banking — mobile-specific API surface

Key principle: each service owned its data. No shared databases. Service-to-service communication happened only via well-defined API contracts — never direct DB calls across boundaries.

2

Migration Strategy — Strangler Fig Pattern

A big-bang rewrite was not an option with a live banking platform. I chose the Strangler Fig pattern — gradually routing traffic from the monolith to new microservices one domain at a time, with the monolith as fallback.

  • Phase 1: Build new microservices behind feature flags — no production traffic yet
  • Phase 2: Route a small % of non-critical read traffic to new services and validate
  • Phase 3: Progressively migrate write operations domain-by-domain, starting lowest risk
  • Phase 4: Decommission monolith modules as migration confidence grew
3

Security Architecture

Security was the most complex challenge. Meridian required OAuth 2.0 with a proprietary OAuth Broker rather than a standard identity provider — meaning no off-the-shelf solution.

  • Designed token lifecycle management with short-lived access tokens and secure refresh rotation
  • Built a global HTTP interceptor handling auth validation, logging, and distributed caching in one cross-cutting layer — eliminating duplicated auth code across 15+ services
  • Implemented 2FA at the API Gateway layer — no individual service needed to handle MFA logic
  • Defined API security standards as a shared library — one change propagated everywhere automatically
  • Established audit logging at infrastructure layer for compliance — no per-service developer action needed
4

Fault Tolerance Patterns

Banking systems cannot have cascading failures. I implemented defensive patterns at the service layer using Resilience4j:

  • Circuit Breakers: Services fail fast when a downstream dependency is unhealthy, preventing cascades
  • Retry with Exponential Backoff: Transient failures recovered automatically without user impact
  • Bulkheads: Thread pool isolation per service type — a slow payments service couldn't exhaust resources for account reads
  • Timeouts on all external calls: No indefinitely hanging requests under load
5

React Platform & BFF Layer

In parallel, I led the frontend architecture for the full retail banking React platform — spanning all migrated banking domains, used by millions of customers.

  • Designed a unified component library shared across all banking modules for visual and behavioral consistency
  • Defined a BFF (Backend for Frontend) layer per major domain to aggregate microservice responses into frontend-optimized payloads — reducing API round trips by ~60%
  • Implemented React Query for server state, eliminating complex Redux boilerplate for data fetching
  • Designed loading, error, and empty states as first-class concerns — critical for financial data display reliability
04 — Key Decisions

Trade-offs & Architecture Decisions

Every architecture decision involves trade-offs. Here's how I thought through the key ones:

Decision Why I Chose It Trade-off Accepted
Strangler Fig over Big Bang rewrite Zero risk to live banking customers — monolith always available as fallback throughout migration Longer migration timeline (~18 months vs ~6 months) — worth it for the safety guarantee
Shared auth library vs service mesh Team familiarity; no service-mesh ops overhead for a 10-person team with tight deadline Some coupling on auth library versioning; mitigated with semantic versioning strategy
Database per service True domain isolation, independent scaling, prevents cross-domain data coupling — required by banking compliance More databases to manage and provision; accepted because regulatory isolation required it
BFF layer per domain Frontend-optimized payloads, reduced round trips, clear domain-aligned ownership model More services to maintain — judged worth it for the user experience and performance gains
OpenShift over managed Kubernetes Mandated by Meridian's existing infrastructure investment and regulatory control requirements Less flexibility than EKS/GKE; worked within the constraint effectively using OpenShift features

06 — Reflection

What I'd Do Differently

Honest retrospective

  • Introduce contract testing (Pact) from day one — we relied on Postman integration tests which caught issues later in the cycle than ideal
  • Invest in an internal developer portal earlier — once we reached 12+ services, discoverability and ownership clarity became a challenge
  • Start distributed tracing on day one — we retrofitted Prometheus/Grafana mid-migration, which was significantly more painful than building observability in from the start
